Provider kubernetes

Se connecter au cluster

  • Le provider kubernetes parle à l’API du cluster
  • Ici, via le kubeconfig de az aks get-credentials
  • En pipeline : les données du cluster viennent d’un data
provider "kubernetes" {  config_path    = "~/.kube/config"  config_context = "aks-prenom"} resource "kubernetes_namespace_v1" "app" {  metadata {    name = "app"  }}
Azure Terraform · Infrastructure AutomationJour 3

Bonne pratique

Deux configurations, pas une

  • Le provider kubernetes a besoin d’un cluster qui existe déjà
  • Dans une même configuration, il tente de se connecter avant que le cluster soit créé
  • Solution : une configuration pour le cluster, une autre pour l’application
  • Elles ont chacune leur state, leur cycle de vie et leur pipeline

À retenir

Cluster et application dans deux configurations : le provider a besoin d’un cluster déjà là.

Module

Le Deployment, dans le module

  • Le module app contient les ressources Kubernetes
  • Les entrées : registre, tag, réplicas
  • Vous l’appelez : vous n’écrivez pas tout
Équivalent YAML
apiVersion: apps/v1kind: Deploymentmetadata:  name: frontend  namespace: appspec:  replicas: 2  # selector, template, containers...  #   image: <registre>/frontend:v1
resource "kubernetes_deployment_v1" "frontend" {  metadata {    name      = "frontend"    namespace = var.namespace  }  spec {    replicas = var.replicas    # selector, template, container...    #   image = "${var.registry}/frontend:${var.tag}"  }}

Appeler le module app

  • Le registre vient d’un data
  • Le tag de l’image est une variable

Exposition

Un Service LoadBalancer

  • type = "LoadBalancer" : Azure crée une IP publique
  • selector : relie le Service aux pods
  • port : exposé, target_port : celui du conteneur
Équivalent YAML
apiVersion: v1kind: Servicemetadata:  name: frontend  namespace: appspec:  type: LoadBalancer  selector: { app: frontend }  ports:    - port: 80      targetPort: 8080
resource "kubernetes_service_v1" "frontend" {  metadata {    name      = "frontend"    namespace = var.namespace  }  spec {    type     = "LoadBalancer"    selector = { app = "frontend" }    port {      port        = 80      target_port = 8080    }  }}
Azure Terraform · Infrastructure AutomationJour 3

Exposition

Récupérer l’adresse

  • L’IP est dans le statut du Service
  • Un output l’affiche à la fin de l’apply
  • Elle est dynamique : pas d’IP statique à payer
locals {  lb = kubernetes_service_v1.frontend.status[0]} output "url" {  value = "http://${local.lb.load_balancer[0].ingress[0].ip}"}

Exposition

Un nom DNS sans configuration

  • Une annotation sur le Service
  • Le nom est fourni par Azure, par région
  • Il doit être unique : préfixez-le de votre prénom
annotations = {  "service.beta.kubernetes.io/azure-dns-label-name" = "tf-prenom"} # Résultat :# tf-prenom.swedencentral.cloudapp.azure.com

resource "azurerm_kubernetes_cluster" "main" {  # ...  kubernetes_version        = "1.36"  automatic_upgrade_channel = "patch"   default_node_pool {    # ...    upgrade_settings {      max_surge = "10%"    }  }}

Exploitation

Tags Azure et labels Kubernetes

  • Les tags Azure servent à la facturation et à l’inventaire
  • Les labels Kubernetes servent à placer les pods
  • nodeSelector choisit un nœud par label
default_node_pool {  # ...  tags = {    owner = var.prenom  }  node_labels = {    role = "system"  }}

Exploitation

L’autoscaler

  • Le nombre de nœuds varie entre min_count et max_count
  • Remplace node_count
  • Le coût suit la charge
default_node_pool {  name                 = "system"  vm_size              = "Standard_D2as_v6"  auto_scaling_enabled = true  min_count            = 1  max_count            = 2}

Troubleshooting

Bonnes pratiques pour éviter une erreur

  • Toujours lire le plan avant d’appliquer
  • Épingler les versions de Terraform et des providers
  • State distant et verrouillé, jamais commité
  • Petites modifications, appliquées souvent
  • fmt et validate dans le pipeline
  • Ne pas modifier à la main ce que Terraform gère

Diagnostic

TF_LOG et refresh-only

  • TF_LOG : journaux détaillés
  • -refresh-only : compare le state à la réalité, sans rien modifier
  • Les journaux peuvent contenir des secrets : ne les partagez pas
# Journaux détaillésexport TF_LOG=DEBUGexport TF_LOG_PATH=terraform.logterraform plan # La réalité a changé hors de Terraform ?terraform plan -refresh-only

Pannes volontaires

Objectif : Diagnostiquer et corriger trois pannes dans une application préparée.

  1. Appliquez la configuration jour3/pannes.
  2. Panne 1 : un pod en ImagePullBackOff : trouvez la cause avec describe.
  3. Panne 2 : le Service n’a pas d’endpoints : comparez selector et labels.
  4. Panne 3 : un apply est verrouillé : levez le verrou proprement.
  5. Relancez plan avec TF_LOG=DEBUG et repérez un appel Azure.

Bonus : supprimez une ressource à la main puis lancez terraform plan -refresh-only.
